---
title: Field-level reactivity
description: Read query and fragment data directly with Svelte 5 reactivity.
---

Field-level reactivity is experimental and disabled by default. Enable it in
`houdini.config.js`, then regenerate Houdini's output and restart your dev server:

```js
export default {
  experimentalFieldReactivity: true,
  plugins: { 'houdini-svelte': {} }
}
```

The top-level option selects the runtime and generates readonly arrays in query
and fragment result types. Projects without the option keep their existing types.
If you used a preview with this option inside `plugins['houdini-svelte']`, move it
to the top level and regenerate.
With it enabled, query stores expose reactive fields directly. Updating one
user's name updates the consumers of that name without rerunning calculations
for every user in the query. The examples below use experimental mode.

```svelte
<script lang="ts">
  import type { PageData } from './$types'

  let { data }: { data: PageData } = $props()
  const users = $derived(data.UsersTable)
</script>

{#if users.fetching}
  <p>Loading…</p>
{/if}

<table>
  <tbody>
    {#each users.data?.users ?? [] as user (user.id)}
      <tr><td>{user.name}</td><td>{user.email}</td></tr>
    {/each}
  </tbody>
</table>
```

`users` is the generated store itself. Keep calling `users.fetch()` and, for
paginated queries, `users.loadNextPage()` on that object. It also exposes
`errors`, `variables`, `partial`, `stale`, `source`, and `extensions`. Cursor
queries expose `pageInfo`.

The `$derived` above follows replacement stores when route data changes. A
fixed store can be read directly without a derived value. Svelte automatically
owns the subscription while reactive consumers read the fields and releases it
when those consumers disappear. SSR reads the current data without subscribing.

## Plain fragments

Plain fragment instances expose their selected fields through `data`:

```svelte
<script lang="ts">
  import { fragment, graphql, type UserRowFields } from '$houdini'

  let { user }: { user: UserRowFields } = $props()
  const row = $derived(fragment(user, graphql(`
    fragment UserRowFields on User {
      name
      email
    }
  `)))
</script>

<tr><td>{row.data.name}</td><td>{row.data.email}</td></tr>
```

Row fragments still limit the scope of cache subscriptions. Field reactivity
also works when a query selects an entire table directly.

## Reading and changing values

Read properties in templates, `$derived`, or `$effect` to track them:

```ts
const name = $derived(users.data?.users[0]?.name)
```

Reading only an object reference tracks its replacement. Read the nested fields
that your calculation depends on. A one-time assignment outside reactive code
captures a value at that moment.

Scalar updates preserve enclosing object and array references. Changes to array
membership or ordering replace the array while retaining surviving keyed record
objects. Adding or removing selected object keys replaces that object. Read lists
through a reactive expression if your code needs to follow those replacements.

Use `$derived` for a local alias that follows cache updates and record replacement:

```ts
const row = $derived(query.data?.case)
```

`$state(query.data.case)` and `$state.raw(query.data.case)` retain a reference to
the current record. Its fields remain reactive while the query has a reactive
consumer, but neither assignment follows record replacement. `$state.raw` avoids
adding a deep proxy when you need a reassignable local reference. A captured
reference does not keep the query subscribed by itself; keep reading the store
in reactive code.

### Avoid spreading rows in a list derived

Spreading a row reads all of its enumerable fields. This derived subscribes to
every field of every row and creates new row objects whenever any of them changes:

```ts
const rows = $derived(
  users.data?.users.map(user => ({ ...user, label: user.profile.name })) ?? []
)
```

For a table library, prefer a column accessor that reads `user.profile.name` when
rendering that cell. If the library requires a flattened property, keep the
original row and expose a getter:

```ts
const rows = $derived(
  users.data?.users.map(user => ({
    user,
    get label() { return user.profile.name }
  })) ?? []
)
```

Creating these wrappers reads only the list and row references. Reading `label`
in a reactive cell tracks that row's name. The library must read the getter in
reactive code for this to work; a library that snapshots all rows still determines
its own update cost. Use `mutable()` below when only a mutable array is needed.

## Readonly results and local copies

Generated query `$result` and fragment `$data` types include readonly arrays
when the option is enabled. Use these types for component props and local aliases;
you do not need to wrap them in `ReactiveValue`. Inputs and optimistic payloads
keep their existing array types. The readonly result types apply throughout the
project, including components that still use `$Query.data`.

Nested selections also have generated names, such as `UsersTable$result$users`.
These aliases appear in type errors and can be imported from `$houdini`. They are
available with either setting of the flag.

Objects and arrays are readonly in TypeScript and reject direct writes at
runtime. Update them through mutations or cache APIs. Standard Dates are copied
and compared by timestamp. Custom scalar class instances remain atomic values;
replace them through the cache rather than mutating them through the view.
Cyclic results are unsupported.

For sorting, use `.toSorted()` where supported, or copy the list with `mutable()`:

```ts
import { mutable } from '$houdini'

const sorted = $derived(
  mutable(users.data?.users ?? []).sort((a, b) => a.name.localeCompare(b.name))
)
```

`mutable(list)` is a shallow `.slice()` copy for APIs that require a mutable array.
It copies membership and order. Items keep their readonly reactive fields, so a
scalar update remains visible through the copied list. Create a new copy in a
reactive expression to follow membership changes. For an editable form, copy the
fields the form owns into local state; this helper does not create an editable
record or deep clone.

With `$derived(mutable(list))`, the copy runs when the list reference changes.
Scalar updates flow through the shared row objects. Adding `.sort()` also tracks
the fields its comparator reads, so changes to those fields rerun the sort.

During migration, an in-place `.sort((a, b) => ...)` on a readonly list can produce
"Parameter 'a' implicitly has an 'any' type" errors. The unavailable `.sort()`
method also removes contextual typing for its callback. Check whether the list is
readonly, then use `.toSorted()` or `mutable(list).sort(...)` to preserve both the
cached order and comparator types.

`ReactiveValue<T>` remains exported from `$houdini` for handwritten types. It makes
plain records and arrays recursively readonly and preserves configured scalar
classes. Generated result types already describe the readonly GraphQL lists.

If a fragment reports a missing cache record, inspect the parent response for the
selected `__typename` and configured key fields. A reference to an evicted or
deleted record can cause the same warning. Fragments with type-specific selections
need `__typename` to choose their fields. Generated concrete fragments also select
a non-null root `__typename`: omitting it makes the fragment read null even when
the cache has correctly keyed the record. The parent query can still render because
it hides that field. Both cases now warn. Include `__typename` on the object where
the fragment is spread; adding it only to nested objects does not fix the root read.

## Existing store code

`$Query.data`, `get(Query)`, and `Query.subscribe()` still work. They use Svelte's
store protocol, which invalidates readers of the whole store value. Use
`Query.data` for field-level dependencies. Imperative subscription callbacks
receive complete snapshots, even when they retain a result for later inspection.

With the option disabled, existing APIs keep their meanings. In experimental
mode, the previous boolean `Query.variables` becomes `Query.requiresVariables`.
`Query.variables` contains the current input values. A plain fragment's `data`
is now its reactive payload; subscribe to the fragment instance itself when you
need a store subscription.

You can use `$Query.data` and `Query.data` together in an enabled project. A legacy
subscriber still requires complete snapshots, so compare separate page runs when
measuring the cost of the two update paths. To turn the experiment off, switch
direct reads back to store subscriptions, disable the option, and regenerate.

## Update cost

Scalar updates use an index of selected cache records. Changing one name does not
reconstruct or compare the whole query. Aliases, configured record keys, masked
IDs, custom scalar conversion, and optimistic scalar rollback use this path.

Relationship changes, null propagation, and resets still read the complete
selection. Initial reads build the field index. Imperative subscribers and
custom client hooks can also require full snapshots. Those costs are separate
from the field update path; timings for a scalar update do not establish the
cost of inserting a page or replacing a whole query result.
